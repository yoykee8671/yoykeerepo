# wooofpay v2 — 우프 ERP 설계 초안

작성: 2026-11-13 · 상태: **초안(대표 검토 대기)** · 브랜치: `v2` (운영 사이트와 분리)

> 한 줄 목표: 지금 시트·노션·채널톡·팩스로 흩어진 "돈·물건·거래처·정산" 일을

> 그 결과를 KPI 공헌이익·손익·목표매출까지 자동으로 잇는다.

| 입점사 정보·담당자 | 오래된 구글시트 | **거래처** (통합 마스터, 상태: 거래중/장기미거래/신규) |

## 2. v2 메뉴 구조 (우리 용어)

```
오늘            ← 첫 화면: 오늘 나갈 돈, 7일 내 나갈 돈, 결재 대기, 처리할 일
자금
  ├ 일일 자금보고   (클로브 잔액 + 나갈 돈 + 들어올 돈 → 하루 한 장, 이미지/링크로 공유)
  ├ 나갈 돈 일정    (계산서 기준 / PG 기준 / 고정금액 / 대출 상환 / 지급요청)
  ├ 받을 돈        (미수금·수금예정)
  ├ 대출금         (베럴즈 / 우프 원장, 이체되면 자동 차감)
  └ 계좌·잔액      (계좌관리 = 이미 만든 기능 포함)
입금요청(선매입)  ← 지금 그대로 + 채권 원장
지급요청          ← 채널톡·노션 결제요청 대체 (요청 → 확인 → 이체양식 → 입금완료, 영수증 첨부)
판매              ← 주문수집 → 명세서 → 업체전달 → 청구·계산서 → 입금확인
생산              ← 생산발주 / 원부자재 재고 / 생산비(미지급)
물류              ← 물류비 정산서 검증, 3PL 출고
정산              ← 입점사 월정산 / NPB
거래처            ← 브랜드·생산업체·도매·납품처·외주 한곳 (역할 여러 개 가능)
품목·단가         ← 품목 마스터 + 판매처별 가격
경영              ← KPI 공헌이익 / 손익 / 목표
인사              ← (마지막)
설정              ← 관리자·권한·코드·사업부
```

**사업부(손익 단위)** — KPI 설계(`kpi/DESIGN.md`)와 AI_CFO 지표정의를 그대로 따라요.

| 사업부 | 내용 | KPI 공헌이익 |
|---|---|---|
| 우프(입점) | 입점브랜드 위탁·선매입 | 포함 |
| PB | 베럴즈 등 자사 생산 | 포함 |
| NPB | 도톤·공감캣·필바이츠(픽키) | 포함 |
| 용역 | 소일베이커 100만, 픽키파크 200만, MIH(베럴즈) 등 | 별도 칸(이중계상 방지) |

모든 돈의 흐름(입금요청·지급요청·판매·생산비·물류비)에 **사업부 꼬리표**를 달아요. 그래야 손익과 KPI가 자동으로 나와요.

## 3. 통합 고유코드 (P0 — 바로 시작)

**왜**: 입금요청의 브랜드가 거래처관리에 또 있고, 원부자재와 단가표 품목이 겹쳐 쓰여요. 이름으로 묶으면 오타와 중복이 생겨요. 그래서 사람이 읽을 수 있는 **고유코드**를 자동으로 붙이고, 연결은 코드로 해요.

| 대상 | 코드 모양 | 예 |
|---|---|---|
| 브랜드 | `BR-0001` | BR-0012 테일릿 |
| 거래처 | `PT-0001` | PT-0003 세림통상 |
| 원부자재 | `MT-0001` | MT-0021 필포켓 파우치 |
| 납품지 | `DP-001` | DP-002 쿠팡 천안센터 |
| 명세서·발주서 | `문서종류-YYMM-001` | `ST-2611-004`(명세서), `PO-2611-001`(발주서) |
| 관리자 | `AD-01` | AD-02 김예빈 |
| 단가표 품목 | `IT-00001` | IT-00153 |
| 입금계좌 | `AC-0001` | AC-0042 |

규칙:
- 한 번 붙은 코드는 **바뀌지 않아요**(이름을 바꿔도 같아요). 지운 코드도 다시 쓰지 않아요.
- 지금 있는 데이터에는 **만든 날짜 순서대로** 한 번에 붙여요.
- 브랜드와 거래처가 같은 회사면 **연결**만 해요(브랜드에 `거래처코드` 칸). 합치지는 않아요. 브랜드는 입금요청·정산 단위, 거래처는 회사(사업자) 단위이기 때문이에요.
- 원부자재와 단가표 품목이 같은 물건이면 **같은 품목코드**를 쓰게 연결해요(다음 단계).

## 4. 큰 설계 결정 (기술)

### 4-1. 저장 방식 (가장 큰 과제)
지금은 DB 전체가 **JSON 한 덩어리**(약 5MB)예요. 누가 뭘 저장하든 통째로 다시 써요. ERP로 커지면(지급요청·재고 이동·자금 일정이 매일 쌓이면) 다음 문제가 생겨요.
- 느려져요.
- 동시에 저장하면 충돌이 나요.
- 기록이 하나라도 깨지면 전체가 위험해요.

★추천: v2는 **새로 만드는 기능부터 별도 표(테이블)**에 저장하고, 기존 기능은 그대로 둔 채 하나씩 옮겨요. 한 번에 갈아엎지 않아요.

### 4-2. 연동
- **클로브(clobe.ai)**: 계좌 잔액·거래내역 → 일일 자금보고, 입금 확인, 대출 상환 자동 반영. 이미 연결돼 있어요.
- **카페24**: 주문 → 입금요청·판매 파이프라인. 이미 연결돼 있어요.
- **AI_CFO**: 원장 분류 규칙과 지표 정의를 v2가 그대로 써요. v2 데이터를 AI_CFO가 읽어 아침 보고에 써요(양방향 중복 입력 제거).
- **kpi.html**: v2 경영 메뉴로 흡수해요. 계산식은 `kpi/DESIGN.md` 그대로예요.
- **채널톡**: 일일 자금보고·지급요청 알림 보내기(웹훅). 키 필요 → §7

### 4-3. 테스트 방식
- v2는 `v2` 브랜치에만 쌓아요. 운영(main)과 섞이지 않아요.
- 맥미니에 **테스트용 사이트**를 따로 띄워요. 운영 DB를 **복사한** 데이터로 돌아가요. 대표님이 여기서 마음껏 눌러 보셔도 운영 데이터는 안전해요. 주소는 §6 결정 필요.

## 6. 결정 필요 (★ = 정하기 전까지 제 추천으로 진행)

1. **코드 모양** — ★§3 표 그대로(`BR-0001` 등). 다른 모양을 원하시면 말씀해 주세요.
2. **브랜드 ↔ 거래처** — ★합치지 않고 연결. 한 회사가 브랜드 여러 개를 가질 수 있어서예요.
3. **판매처별 가격** — ★"품목 기준가(정가) + 판매처별 가격정책" 2단.
   - 가격정책 = 할인율(%) 또는 고정 공급가 중 하나
   - 판매처 × 품목 예외만 따로 적음
   - 예: 필바이츠 45g 정가 15,000 / 쿠팡 공급가 9,000(고정) / 컬리 할인 35%
4. **일일 자금보고 공유 방식**
   - ★1차: v2 화면을 이미지로 저장 + 링크 → 채널톡에 붙여넣기
   - 2차: 채널톡 자동 전송(키 필요)
5. **예측 범위** — ★오늘 + 7일(매일), 월말까지 요약 1줄.
6. **지급요청 승인** — ★요청자 → 김예빈 확인 → (금액 100만원 이상만) 대표 승인. 기준 금액은 바꿀 수 있어요.
7. **테스트 사이트 주소**
   - ★`v2.gnuol.com`(Cloudflare 터널에 주소 한 줄 추가 — 대표님 대시보드 작업 5분)

## 9. 판매처별 가격 체계 (구현됨 — 판매 > 판매처 가격)

**문제**: 같은 제품(PB·NPB)도 판매처마다 할인율·공급가가 다르고(쿠팡 고정 공급가, 컬리 할인율, B2B몰은 포함가 기준 등), 지금은 단가표·NPB 채널 설정·명세서 단가가 따로 놀아 어느 값이 맞는지 알기 어렵다.

**구조 (3단)**

1. **품목** — 단가표 품목(우프코드 `IT-`)이 기준. 품목마다 **기준가**(정가·소비자가, VAT 포함) 하나.
2. **판매처** — 판매처마다 코드(`CH-`)와 **기본 규칙** 하나:
   - 유형: 자사몰 / 오픈마켓 / B2B몰 / 도매 / 오프라인 / 공구
   - 가격 방식: `정가 대비 할인율` · `정가 대비 공급률` · `고정 공급가`(품목별)
   - 금액 기준: VAT 포함 / 별도 (포함이면 §결정 반영된 역산 규칙)
   - 끝전 처리: 원 단위 / 10원 / 100원 (반올림·절사)
   - 판매수수료율(정산·KPI용)
   - 거래처(우프코드 `PT-`)·NPB 채널 코드와 연결 → 명세서·정산·KPI가 같은 판매처를 본다
3. **판매처 × 품목 예외** — 기본 규칙과 다른 칸만 적는다. 고정 공급가 또는 할인율, **적용 기간**(시작·종료) → 기간 지나면 기본 규칙으로 돌아감(행사가). 가격 이력이 남는다.

**값을 찾는 순서**: 판매처 × 품목 예외(기간 안) → 판매처 기본 규칙 → 품목 기준가. 어느 단계에서 나온 값인지 화면에 같이 보여 준다.

**모르는 칸 채우기(최초 세팅)**: 판매처에 규칙이 없거나, 명세서·정산에 쓴 단가가 계산값과 다르면 **확인 필요** 질문을 만든다.
- 예: "쿠팡 · 필바이츠 45g 공급가는? (최근 명세서 9,000원 / 규칙 없음)" → [9,000원 고정] [할인율 입력] [이번만]
- 답하면 예외 또는 규칙으로 저장되고, 같은 질문은 다시 나오지 않는다.

**씨앗 데이터**: 단가표(공급가·원판매가), NPB 채널 설정(판매가·수수료율), 지난 명세서 단가에서 후보를 뽑아 질문의 선택지로 제시한다.

**구현 메모 (2026-11-14)**
- 판매처 `db.salesChannels`(우프코드 `CH-`), 예외 `erp_records/channelPrices`(지우지 않고 해제 — 이력).
- 품목: NPB 제품(`npb:`) + 사업부가 PB·NPB인 브랜드의 단가표 품목(`it:`). 브랜드 사업부를 지정하면 자동으로 늘어난다.
- 예외는 가격만·수수료만·둘 다 가능(브랜드마다 수수료가 다른 판매처).
- 'NPB 채널에서 가져오기': 같은 판매처(coupang / picky_coupang)를 하나로 묶고, NPB 공급가 → 고정가 예외, 브랜드별 수수료 → 수수료 예외, 기본 가격 방식 → 확인 필요 질문. 여러 번 눌러도 안전.

## 10. 생산비 (구현됨 — 생산·재고 > 생산비)

## 11. 대출금 원장 (구현됨 — 자금 > 대출금)

- 대출(erp loans)은 시트 한 줄 = 대출 하나. 시트 '잔여 대출금'을 기준일(asOf, 2026-07-24) 잔액으로 두고, 그 뒤 상환 원금(loanPayments)을 빼서 지금 잔액을 계산한다.

- 확인 필요: 만기 지난 대출 8건(우프 '매년만기/연갱신' 3건 포함) → [연장됨·새 만기일] [다 갚음].
- **회생채권 전환**(대표 확인 2026-11-15): 우프 대출 5건은 모두 회생채권에 들어갔다 — 신한 일반자금 3억·2억·5억 → 기술보증기금, 기업 임금채권보장기금 4,500만 → 근로복지공단(대위변제로 명의 변경), 신한 청년창업 6,578만 → 중소벤처기업진흥공단. 대출 `rehabCreditor` 칸에 적으면 상태 '회생채권'이 되어 은행 상환·이자 일정·클로브 매칭·대출 합계에서 빠지고(따로 '회생채권으로 전환' 합계), 만기 질문은 자동으로 닫힌다. 시트에 없는 사실이라 `~/.cache/v2data/loan/overrides.json` 에 두고 `scripts/v2test-up.sh --overrides`(또는 --reset)가 가져오기 뒤에 다시 적용한다.

## 18. 사업자·브랜드·매출 분류 (대표 지침 2026-11-15)

- 원문(개인 정보 포함)은 저장소에 넣지 않는다. 규칙만 적는다.
- **사업자와 브랜드는 다른 칸.** 같은 이름이 둘 다 있다: Betters(브랜드 = 우프컴퍼니 PB 매출 / 개인사업자 Betters = 상품 매출 없음, 대출 상환용·교영 개인 용역), 픽키파크(사업자 = 박상민 대표 개인사업자 / 브랜드 = 사람 식품).
- v2 의 `company: "betters"` 는 **개인사업자 Betters**. 화면 표기를 'Betters(개인사업자)'로 바꿨다(이전 '베럴즈').
- 매출 유형: product_sales · agency_fee(픽키도기클럽 운영대행비 = max(200만, 월매출×10%)) · consigned_sales(픽키도기클럽 대행 판매분 — 정산 대상, 우프 매출 아님) · cost_rebill · service_fee(소일베이커, ITIT) · pass_through(ITIT 500만 중 비스타디아 측 300만 — 순매출에서 뺌). 현금흐름표 행에 매출 유형 칸을 두었다.
- 귀속: 우프 직원·인프라를 쓰면 우프컴퍼니, 교영 개인 역량만이면 개인사업자 Betters. YMCA·식품 브랜드 픽키파크는 우프에 넣지 않는다. 애매하면 확인 필요.
- 바로잡음: 미수·미지급 시트 'MIH' 탭은 MIH → Betters(개인) **받을 돈** 550만/월(ITIT 운영 용역), 'BETTERS-FOM' 칸은 Betters(개인) → 비스타디아 측 **재발행 지급** 330만. 앞서 방향을 반대로 제안했던 것을 고쳤다(답하기 전이라 영향 없음).

## 22. 왕복 줄이기 (2026-11-15)

## 25. 운영(pay) → v2 하루 한 번 합치기 (대표 결정 2026-11-16)

- v2 를 완성할 때까지 직원은 pay 를 쓰고, 대표는 v2 에 자료를 채운다. 매일 04:10 `scripts/v2-sync.sh`(LaunchAgent `com.yoykee.wooofpay-v2sync`)가 운영 상태를 읽어(운영은 읽기만) v2 에 합친다.
- 3-way 합치기(`lib/sync-merge.mjs`): 기준점 = 지난번 운영 상태(처음은 v2 복사 직전 백업 2026-11-14). 칸마다 운영만 고쳤으면 운영 값, v2 만 고쳤으면 v2 값, 둘 다 다르게 고쳤으면 v2 값을 두고 '확인 필요'(kind `sync-conflict`)로 묻는다 — 'pay 값으로'를 고르면 그 칸에 운영 값을 넣는다. `{id}` 배열은 id 로 맞춘다. 클로브·카페24 토큰과 리비전은 v2 것 그대로.
- 합치기 전 v2 상태를 `~/.cache/v2data/sync/v2-before-*.json.gz` 로 7일치 남긴다. 기록: `~/.cache/v2data/sync/sync.log`. `--dry-run` 으로 미리 볼 수 있다.
- 전환하는 날: pay 사용을 멈추고 마지막으로 한 번 더 합친 뒤 pay 를 v2 코드·데이터로 바꾼다. v2 에서 연습으로 만든 기록은 그 전에 지운다.
