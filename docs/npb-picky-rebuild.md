## 1. 픽키 정산서는 도톤과 구조가 다르다

도톤 것을 고쳐 쓸 수 없다. 시트 구성부터 다르다.

| | 도톤 | 픽키 |
|---|---|---|
| 1장 | 종합정산 (재고·실비·이익분배 한 장에) | **정산서** (판매종합 + 계산서발행 안내만) |
| 2장 | 채널별 판매데이터 정리 | **채널별 정산 합계** (신설) |
| 3장 | DB)입출고목록 | 채널별 판매데이터 정리 |
| 이후 | 채널 원본 | 채널 원본 (`DB)coupang` 등) |

### 픽키에만 있는 것 — 정산 주체 분리

`채널별 정산 합계`의 각 채널 블록에 **정산형태**(우프 / 픽키파크) 칸이 있고,
`정산서`가 그 둘을 나눠 합친다.

```
정산서 C11 = '채널별 정산 합계'!F26 + F34        (픽키파크 정산)
정산서 C12 = '채널별 정산 합계'!F6 + F22 + F42   (우프 정산)
```

- **우프 정산** — 우프가 수수료 계산서를 발행하고 정산금을 입금
- **픽키파크 정산** — 업체가 픽키파크로 직접 발행·입금 (우프는 전달만)

도톤에는 없는 개념이라 데이터 모델에 `settleBy`(이미 채널에 있음)를 정산서
집계까지 끌어와야 한다.

### 채널 블록의 칸

```
항목 · 정가합계 · 배송비합계 · 할인합계 · 최종결제합계 ·
공제(%) · 공제(원) · 정산합계 · 정산형태 · 비고
```

공제(%)는 숫자가 아닌 경우가 있다 — `품목별상이`(쿠팡), `네이버기준`.
배송비합계도 `쿠팡배송`·`자체배송`·`매장위탁판매` 같은 글자가 들어간다.
**숫자 칸에 글자가 들어갈 수 있다는 전제로 써야 한다.**

### 매출 없는 채널은 숨김

8월 기준 숨긴 행: 8~19, 28~31, 36~39 (betters_sm_st, wooof-B2B, 테일릿,
kurly, 파마스퀘어). 지우지 않고 **행 숨김**으로 둔다 — 채널 목록 자체는
유지해야 다음 달에 되살리기 쉽다.

## 2. 수식이 사라지는 이유 — 원인 확인·수정 완료

세 장을 수식으로 묶었다. 생성기가 값만 찍고 있었던 것이지 방법이 없는 게
아니었다.

```
정산서 D6~G6      → '채널별 정산 합계'!I45~I49   (요약 줄)
정산서 C11~E12    → 합계 시트의 주체별 채널 줄 합
합계  C/D/E 각 줄 → '채널별 판매데이터 정리'!E/F/G (채널 합계 줄)
합계  F = C-E+D,  H = F*G (요율이 숫자인 채널),  I = F-H
합계  43행        = SUM(5:42),  45~49행 = 그 줄 참조
판매  H = E+F-G,  J = H*I,  K = H-J,  합계 = SUM(블록)
```

### 양식과 셀 단위로 맞춘 것

| | 맞춤 |
|---|---|
| 글꼴 | 맑은 고딕 — 정산서 10pt, 나머지 11pt |
| 열너비 | 세 장 모두 양식 값 그대로 (예: 합계 K 65.2, 판매 C 75.5) |
| 줄 위치 | 43 총계 / 44 VAT포함 / 45~49 요약 / 50~51 주체별 — 양식과 동일 행 |
| 서식 | 총계 줄만 회계서식, 공제(%) 0.0%, 나머지 #,##0 |
| 테두리·정렬·배경 | 머리 D9D9D9, 채널명 F2F2F2, 합계 E2EFDA, 우프줄 FBE3D6 |
| 숨김 | 매출 0 인 채널은 블록+빈 줄까지 접음 → 8~19, 28~31, 36~39 (양식과 일치) |
| 시트 순서 | 정산서 → 합계 → 판매데이터 → DB) |

**대조 결과** (사람이 만든 8월 파일을 LibreOffice 로 계산시킨 값이 정답지):

```
소비자정가합계 4,643,400 OK        최종결제액 4,816,649 (생성 4,816,649.1)
공제합계 1,100,536.15 (생성 .185)  정산 3,716,112.85 (생성 .915)
우프 1,008,780 OK                 픽키파크 2,707,332.85 (생성 .915)
채널별: cafe24·coupang·smartstore·몽슈슈 전부 일치
```

차이는 전부 **sparkpet 소수점** 한 군데서 나온다 — 스파크펫 정산서의 할인이
21,234.84 + 18,516.06 = 39,750.90 인데 사람이 만든 표는 39,751 로 올려 적었다.
구조 문제가 아니라 아래 '채널별 끝자리 처리' 설정으로 해결할 사안이다.

### 서버 쪽도 같이 고침

`npbBuildPickySpec` 이 **내역이 있는 채널만** 넘기고 있었다. 양식은 채널을 다
세워 두고 줄만 숨기므로, 브랜드의 채널 전체를 넘기도록 바꿨다. 또 채널의
`feeRate` 를 안 넘겨 공제액 수식(`=F*G`)이 걸리지 않던 것도 고쳤다.

### 남은 차이 (알려 둘 것)

양식은 채널마다 **상품표 전체 10줄**을 세워 두고 안 팔린 품목도 0 으로 남긴다.
생성기는 **팔린 줄만** 적는다. 숫자는 같지만 줄 수가 다르다 — 어느 쪽이 좋은지
확인 필요.

## 5. DB 파일 파싱 — 무엇이 깨져 있었나 (수정 완료)

받은 원본 10개를 전부 파서에 통과시켜 확인했다.

| 파일 | 전 | 후 |
|---|---|---|
| cafe24 판매내역 (csv) | **0줄** | 2줄 (옵션별로 나뉨) |
| 쿠팡 입고완료 내역 | **0줄** | 3줄 · 정산 923,100 |
| 몽슈슈 판매내역 | **0줄** | 1줄 · 수량 6 |
| 네이버 결제정산 | **0줄** | 10줄 · 2,109,200 / 213,000 / 109,749 |
| 대한통운 물류출고 (.xls) | **읽기 실패** | 17줄 |
| 기말재고 (csv, CP949) | **읽기 실패** | 4줄 |
| 스파크펫 위탁판매내역 | 5줄 | 5줄 (다른 브랜드 품목 섞임 — 7절) |
| 신고용자료 | 0줄 | 0줄 (판매내역이 아님 — 7절) |

### 원인 1 — 못 알아본 줄을 버렸다

`identify_product()` 는 도톤 두 품목(풋클리너·스프레이)만 안다. 다른 브랜드
품목은 전부 `unrecognized -> continue` 로 빠졌다. 서버에는 **상품명 매칭**
구조가 이미 있는데(`npbResolveLines` → 미매칭 목록 → 화면에서 한 번 지정 →
별칭 저장), 파서가 먼저 버려서 그 화면에 뜰 것이 없었다.

→ 버리지 않고 `productKey: null` + 원본 이름으로 넘긴다.

별칭의 열쇠는 `raw.code` 와 `raw.sourceName` 다. 그래서:

- **쿠팡** — 묶음(1개·3개·5개)의 SKU명이 모두 같고 SKU번호만 다르다.
  SKU번호를 `code` 로 넘긴다. 집계 열쇠에도 code 를 넣었다 (안 넣으면 세
  묶음이 한 줄로 뭉개진다).
- **카페24** — 옵션(`수량=5개`)이 묶음을 가른다. 이름에 옵션을 붙여 기억한다.
- **몽슈슈** — 제품명이 영문(`Pill Bites`)이고 상품코드가 안정적이라 코드로.

### 원인 2 — 양식을 못 알아봤다

- **네이버 결제정산 - 일별상세**: `수량` 열이 없다. 열을 못 찾자 표를 통째로
  버렸다. 양식 그대로 읽게 했다 — 한 줄 = 1건, `구분`이 배송비면 배송비
  매출, 수수료는 음수 세 칸의 합. 스캐너 경로도 수량 열이 없으면 한 줄을
  1건으로 센다(전에는 0이라 판매수량이 통째로 0).
- **.xls**: 이미 이미지에 있는 LibreOffice 로 변환해 읽는다. 매달 다시
  저장하게 할 일이 아니다.
- **CSV 인코딩**: UTF-8 → CP949 → EUC-KR → UTF-16 순으로 시도. 재고
  내보내기가 CP949 라 통째로 못 읽혔다.

### 채널별 샘플 양식 다운로드

`npb_parse.py` 에 채널별 양식표(`CHANNEL_FORMS`)를 한 곳에 두고, **파서도 그
표에서 열 이름을 읽는다**. 양식과 파서가 갈라져 "양식대로 올렸는데 파싱이
안 된다" 가 되는 일을 막는 것이 목적이다.

```
GET /api/npb/sample-form?channel=<코드>   → 샘플양식_<채널명>.xlsx
```

1행은 파서가 찾는 머리글 그대로, 2행부터 예시, 별도 `작성방법` 시트에 필수
열·집계기준·채널별 주의사항. 업로드 화면의 채널마다 [샘플양식] 버튼.

양식 10종을 **만들어서 다시 파서에 넣어 보는 왕복 시험**으로 확인했다
(`sample_roundtrip.py`, 10/10 통과). 스파크펫처럼 판매처가 자기 양식으로
주는 채널은 정해진 양식이 없다고 안내한다.

## 6. 정가 / 기준가 / 할인 — 지금 동작

워크시트 칸의 뜻은 이렇다.

```
정가   = 소비자 정상가 (상품표 값)
기준가 = 그 채널에서 실제로 팔린 개당 단가 (할인·프로모션 반영 후)
할인   = 정가 − 기준가 (개당)   ← 계산 결과라 입력칸이 아니다
매출계 = 기준가 × 수량
```

할인이 입력칸이 아닌 이유는, 정가와 기준가가 있으면 할인은 자동으로 정해지기
때문이다. 다만 **할인을 먼저 알고 기준가를 모르는 경우**가 있어, 할인에
적으면 기준가가 역산되도록 바꾸는 편이 낫다(검수표는 이미 그렇게 동작한다).

## 7. 확인 필요 (파싱 쪽)

### 신고용자료 파일은 무엇으로 쓰는지

→ 이 파일은 올리지 않는 쪽인지, 아니면 "신고 총액 확인용" 으로 따로 받는
자리를 만들지 확인 필요.

### 스파크펫 파일에 다른 브랜드 품목이 섞여 온다

8월 파일에 도톤 포레스트 스프레이·풋클리너, 베럴즈 포포타올이 함께 있다.

사람이 3줄을 무시해야 한다.

### 몽슈슈 파일의 금액은 정산액이다

파일의 `단가 4,080` 은 정가(6,800)가 아니라 **40% 공제 후 정산단가**이고
`판매합계 24,480` 도 정산액이다. 스캐너는 이걸 매출로 집는다.

정산서의 정답은 정가 40,800 / 수수료 16,320 / 정산 24,480 이므로, 이 채널은
`saleBasis: "list"`(상품표 정가 기준) + `feeBasis: "rate"` 가 맞다.

→ 채널 설정값이라 **확정된 과거 달에 영향이 가지 않는지** 먼저 정리한
다음에 바꾼다 (4절의 스냅샷 항목과 같은 사안).

## 8. 채널별 끝자리 처리 (완료)

채널 설정에 **끝자리** 칸을 넣었다. `그대로 / 반올림 / 올림 / 내림`.

```
채널 설정 > 끝자리  → 화면(npbRowMath) · 서버(npbComputeLine) · 엑셀 수식
엑셀은 =ROUND / =ROUNDUP / =ROUNDDOWN 으로 감싼다 — 셀을 눌러 검산해도 맞게
```

### 확정된 달이 안 바뀌는 방법

**기본값은 '그대로'** 다. 설정을 안 켠 채널은 지금과 똑같이 계산되므로, 이
기능이 생겼다는 이유만으로 과거 금액이 달라지지 않는다.

그리고 줄을 저장할 때 **그 줄이 어느 규칙으로 계산됐는지 함께 저장한다**
(`line.rounding`). 계산할 때 저장된 값이 채널 설정보다 우선이므로, 나중에
채널 설정을 바꿔도 이미 저장·확정된 달은 그대로다.

### 8월 스파크펫에 적용해 보면

`올림` 으로 두면:

```
할인 39,751   최종결제 1,089,049   공제 381,168   정산 707,881   (전부 정수)
최종결제 = 공제 + 정산 으로 떨어진다
```

사람이 만든 8월 표는 **할인만 올림**하고 공제는 소수(381,167.15)로 뒀다.
그래서 공제·정산이 1원씩 다르다. 지금 방식은 파생 금액(할인·최종결제·공제·
정산)을 모두 같은 규칙으로 떨어뜨린다 — 원 단위로 떨어지는 쪽이 받는 쪽에서
검산하기 쉽다고 보았다. 공제만 소수로 남기길 원하면 분리할 수 있다.

## 9. 상품표 전체를 세우는 판매데이터 시트 (완료)

`npbBuildPickySpec` 이 상품표(상품 × 묶음) 순서로 줄을 세우고, 안 팔린 품목은
0 으로 채운다. 줄 위치가 매달 같아야 지난달과 나란히 놓고 볼 수 있다.

픽키는 45g치킨 1·3·5·10개 / 180g치킨 1개 / 45g비건 1·3·5·10개 / 180g비건 1개
= **10줄**, 양식과 같은 순서다. 상품표에 없는 줄(아직 매칭 안 된 판매처 상품)은
뒤에 그대로 붙인다 — 숨기면 합계와 줄의 합이 안 맞아 보인다.

## 10. 재고 입출고 파싱 (완료) — "맨날 오류" 의 원인 세 가지

재고·물류 파일은 판매내역과 **다른 파서**(`xlsx_to_json.py`)를 탄다. 그쪽에
세 가지 문제가 있었다.

### (1) 업로드 파일을 무조건 `.xlsx` 로 떨어뜨렸다

`parseBankXlsxUpload` 가 확장자를 보지 않고 `.xlsx` 로 임시 저장했다. 그래서
대한통운이 주는 **구형 .xls** 와 재고 내보내기 **CSV** 가 openpyxl 에서 바로
터졌다. 파일명을 함께 넘겨 실제 확장자로 쓰고, .xls 는 LibreOffice 로
변환하고, CSV 는 인코딩을 차례로 시도한다.

파일 읽기(.xls 변환 · CSV 인코딩)는 `scripts/sheet_io.py` 로 빼서 판매내역
파서와 함께 쓴다 — 한쪽만 고치면 다른 쪽이 또 깨진다.

### (2) 첫 시트가 자료 시트라는 보장이 없다

사람이 집계 시트(`합포기준`)를 덧붙여 보내면 첫 시트를 집는 규칙이 위험하다.
머리글이 가장 많은 표를 고르게 했다. `read_only` 모드의 잘못된 dimension 도
다시 잡는다(판매내역 파서에 이미 있던 처리).

### (3) 상품 이름 매칭이 픽키를 한 건도 못 잡았다

`npbInventoryFromLogistics` 만 단순 비교(`name.includes(k)`)를 쓰고 있었다.
픽키 상품의 `nameKeywords` 는 중첩 배열(바깥 AND / 안쪽 OR)이라 이 비교로는
항상 거짓이고, 제외 키워드도 안 봐서 45g 출고가 180g 에 붙을 수 있었다.
판매내역과 같은 매칭기(`npbMatchProduct`)를 쓰게 했다.

### 결과 (8월 원본)

```
대한통운 물류출고 (.xls, 119행)   45g치킨 출고 346   45g비건 출고 272
로젠 본사출고 (23행)              45g치킨 출고   7   45g비건 출고  10
기말재고 (CSV, CP949, 4행)        읽힘
```

이름에 용량이 없는 줄(`필바이츠 비건`, `비건 샘플`, `필바이츠 선물`)은 45g·180g
을 가릴 수 없어 미매칭으로 남긴다 — 짐작해서 붙이지 않는다.

## 11. 확정월 기준 고정 (완료) ⭐

가장 중요한 항목이었다. 실비 단가나 정가를 고치면 **이미 보낸 과거 정산서의
금액까지 소급해 달라졌다.**

### 무엇이 소급됐나

정산 하나를 계산할 때 매번 지금의 설정을 읽는 자리가 셋이었다.

| 읽던 것 | 영향 |
|---|---|
| 브랜드 `costConfig` | 실비 합계 (3PL·본사출고 단가, 포장비) |
| 채널 설정 | 수수료율·계산방식·끝자리 — 다만 수수료율은 줄에 함께 저장되어 실제 영향은 없었다 |
| 상품표 `products` | **정가** — `npbListPrice` 가 "상품표가 유일한 출처" 라서 매번 다시 읽는다 |

### 고친 방식

기준값 묶음을 한 함수로 모았다.

```
npbBases(db, settlement)
  확정(final) + 스냅샷 있음  →  스냅샷의 costConfig / channels / products
  그 외                      →  지금의 설정
```

계산(`npbRecompute`), 정산서 엑셀(도톤·픽키 둘 다), 재고현황, 채널 원본 시트,
**실비 청구서**가 모두 이 함수를 쓴다 — 한 곳이라도 지금의 설정을 직접 읽으면
그 문서만 조용히 달라진다.

`정산 확정` 을 누르면 그 시점의 기준을 통째로 떠서 정산에 저장하고(`bases`),
그 기준으로 한 번 다시 계산한다. 순서가 중요하다 — 기준을 먼저 박아야 저장된
숫자가 스냅샷으로 계산한 결과와 정확히 같아진다.

금액에 닿는 칸만 고르지 않고 **설정을 통째로** 담는다. 어느 칸이 금액에
닿는지는 코드가 바뀌면서 달라지고, 그때 스냅샷에서 빠진 칸이 있으면 또
조용히 과거가 흔들린다.

`확정 해제` 를 누르면 스냅샷을 지우고 지금의 기준으로 다시 계산한다. 금액이
달라질 수 있다고 미리 묻는다.

### 확인

```
확정 전       정가계 680,000  공제 238,000  실비    40,800  draft
확정 직후     정가계 680,000  공제 238,000  실비    40,800  final [기준고정]
  ↓ 기준 변경: 3PL 실비 99,999 / 45g치킨 정가 6,800 → 1
기준 변경 후  정가계 680,000  공제 238,000  실비    40,800  final [기준고정]   ← 유지 OK
확정 해제 후  정가계     100  공제      35  실비 1,999,980  draft              ← 잠금이 실제로 잠궜다는 증거
```

스냅샷이 없었다면 확정월이 **정가계 100 / 실비 1,999,980** 으로 변했을
것이다. (시험: `scratchpad/snapshot_test.mjs`)
